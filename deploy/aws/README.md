# AWS operator infrastructure candidate

Concrete platform option for the small Compose service: **EC2 + separate encrypted EBS + Elastic IP + Systems Manager**. Terraform creates no resources during `init`/`validate`. **No `apply`, paid resource, cloud account connection or live service is authorized/provisioned by this candidate.** Compute, EBS, public IPv4 and monitoring can incur charges; the operator must approve the actual regional plan and budget before applying it. End users never interact with Terraform, EC2 or a VPS.

Inputs deliberately require the operator's actual region, VPC/subnet, reviewed compatible AMI and instance size. Use an operator-reviewed supported Linux image with SSM Agent and Docker/Compose, persistent egress and sufficient memory for two isolated Harness profiles; the current container limits total about 4 GiB before OS overhead. Do not guess a cross-region AMI or purchase an instance from a placeholder. No provider/model/identity/signing secret is placed in Terraform variables or state.

The security group exposes only 80/443; administration uses the authorized AWS SSM console, not public SSH. IMDSv2 is required with hop limit **1 deliberately**: the host's SSM agent can use its role, while these untrusted agent containers do not need instance-profile credentials. AWS generally recommends hop 2 when containers themselves need metadata; that is not this deployment's requirement. Do not raise the hop limit or use host networking without reviewing this boundary. Restrict the IAM role further to the actual operator's organization policy before production approval.

After an approved apply, verify the returned data-volume ID and filesystem using the private operator console. Initialize a **new confirmed empty volume only**, or mount an existing compatible filesystem without formatting it. Mount by filesystem UUID at `/srv/always-on-state`, then configure Docker's `data-root` there before starting the service. This keeps the Compose named volumes off the disposable OS disk. Back up Docker configuration, operator secrets and deployment SHA separately. The data volume has `prevent_destroy`; instance replacement must reattach that volume in the same AZ or restore the full coordinated checkpoint, never silently start with empty state.

Install the exact source SHA and follow [the control-plane operator setup](../control/README.md). Configure actual Auth0, DeepSeek, trusted domain/TLS and Expo/APNs/FCM through private secret files. Only after verifying the live service, bake its origin into native builds and obtain authorized signing/distribution. Set up actual CloudWatch/SSM health/disk/instance alarms and a verified operator alert destination. No alert recipient or billing policy has been configured here. EC2 health monitoring is enabled in the template; it is not an application-level alert acceptance result.

Use `terraform init -backend=false` and `terraform validate` for unauthenticated schema checks. Keep a reviewed provider lockfile and encrypted remote state before production; authenticate with the operator's short-lived AWS credentials, inspect the complete `terraform plan`, and obtain the required paid-resource approval before any `apply`. CI never applies or destroys this infrastructure. A valid Terraform schema is not a cloud deployment or Level 5 evidence.

Primary references: [Terraform EC2 instance](https://registry.terraform.io/providers/hashicorp/aws/6.43.0/docs/resources/instance), [AWS IMDS options](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-IMDS-new-instances.html), [AWS metadata access](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-service.html).
