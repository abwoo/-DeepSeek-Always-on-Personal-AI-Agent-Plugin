# Operator-managed v0.3 service

This directory is an implementation/template, **not a provisioned cloud service**. Ordinary Desktop/mobile users only sign in; they never perform these steps. No cloud, Auth0, provider, Expo or Apple account is authorized in this workspace. Do not substitute a worker/PWA or GitHub runner for persistent Harness compute.

## Small production topology

One Caddy edge, one identity/provisioning controller, two preallocated **independent** native Harness containers with separate `/data` and `/config` volumes. Each slot can serve exactly one issuer+subject account. SQLite uniqueness plus a persisted leaf account binding prevents double assignment, owner collisions and accidental takeover of nonempty v0.2 authorities. Full capacity yields provisioning/unavailable, never another user's Host. Add empty isolated slots for capacity; do not duplicate an existing volume or owner identity. No new Agent loop exists in the controller.

The controller exposes only account login/discovery and a whitelist of device endpoints. It substitutes a per-device internal credential when routing to that account's assigned leaf. Upstream owner APIs are never proxied. Per-device external tokens expire in 15 minutes; controller refresh handles rotate, and actual OIDC refresh runs before renewal. Provider-refresh ambiguity requires sign-in. Server-held identity/upstream material is AES-GCM encrypted with an operator key that must survive controller replacement. Device/API revocation is immediate; idempotent leaf/provider cleanup is queued durably and retried after outages. Push may not be claimed disabled upstream until that cleanup is confirmed.

## Authorized operator setup

1. Provision continuous Linux compute and persistent volumes with an authorized cloud account and payment/budget decision. The Compose template requires roughly 4 GB or more and one writer per SQLite/profile. Set a provider-side spend limit as well as model budgets.
2. Register one **Auth0 regular web application** with the tenant's actual issuer, client ID and client secret. Enable authorization code, S256 PKCE and rotating expiring refresh tokens/offline access. Disable password/implicit grants. Register exactly `https://YOUR-SERVICE/account/v1/callback`. Configure Universal Login/account recovery and permitted connections there. The native apps open the system browser; the backend exchanges the OIDC code and validates state, nonce, signature, issuer and audience. No DeepSeek OAuth feature is assumed.
3. Copy `control.json.example` to ignored `operator/control.json`, replace the real service/issuer/client metadata, and preserve the documented exact trusted proxy addresses. The Compose edge IP is `172.31.80.2`; choose a nonconflicting private subnet if needed and update both files. No broad private subnet is trusted as an identity proxy.
4. Under ignored `operator/secrets`, supply: `control-encryption-base64` (32 random bytes in canonical base64), `auth0-client-secret`, `deepseek-key`, independent >=32-character `agent-a-provisioning` and `agent-b-provisioning`; internal CA certificate `internal-ca.pem` and independently signed leaf certificate/key pairs with DNS SAN `agent-a` / `agent-b`. The private CA is for container-to-container TLS, not a public certificate. Do not copy a CA private key into any runtime. Mounts give each agent only its own keys and common provider configuration; the controller does not receive the model key.
5. If push is not yet authorized, keep `ALWAYS_ON_EXPO_PUSH_ENABLED=0` and supply an empty `expo-token` file for the read-only mount. With an actual matching Expo project and APNs/FCM configuration, enable push and provide the server access token via that file. Store Android/Apple signing material in authorized platform credentials, never git.
6. Copy `Caddyfile.example` to ignored `Caddyfile`. Set `ALWAYS_ON_PUBLIC_HOST` and a verified `DEEPSEEK_MODEL` in the **operator environment**. Point authorized DNS at the host; allow only 80/443 inbound. Caddy obtains real public HTTPS for that actual domain. Pool ports and controller 4080 must not be publicly published. Run `docker compose -f deploy/control/compose.yml config --quiet`, build, then `up -d`. The template is not deployed by CI.
7. Check health and logs without tokens, register two real test accounts and prove allocation/access isolation. Compile the actual trusted origin into `config/public-service.json` and reproducible native clients. This public metadata contains no model/owner secret. Missing service config intentionally leaves a development sign-in-unavailable state; do not publish such a candidate as a usable release.

## Budgets, supervision and maintenance

Compose sets restart, memory/CPU/process limits and a private controller health check. Add the cloud provider's actual monitoring/alert destination and persistent-disk alerts once authorized. There is no configured alert recipient in this repository. Native Schedule/task budgets remain; bound account profiles additionally cap simultaneous native turns (2), turn time (180 seconds), turn steps (8), admitted steps per UTC day (300), reported tokens per UTC day (250,000) and output tokens (2,048). Missing reported usage blocks further admission that day. One dispatched request and native/provider retries can overshoot token accounting; auxiliary search charges are separate. These limits are not a guaranteed monetary charge. Only the documented read-only/personal-agent tools are permitted; external writes, local files and shell are denied without a separately implemented reviewed device/approval capability.

`scripts/control-admin.mjs` operates on the private schema-2 controller DB (WAL/busy timeout permits the live controller). `suspend-access` and `disable-account` persist denied access and immediately request a revisioned execution denial from the assigned authority; they are different account flags. Set `ALWAYS_ON_CONTROL_CONFIG` to the matching private controller config for immediate authority contact. A confirmed reply reports execution disabled; missing/unreachable/mismatched authority reports **`stop_pending`, exit 1**, not success. Keep the desired denial persisted and inspect the authority; do not clear it to hide a failed acknowledgement. `resume-access` leaves separately disabled accounts disabled; `enable-account` leaves separately suspended accounts suspended. Renewal is pending until the supervisor confirms it. Suspension before allocation is retained too.

Both isolated account profiles **must** start with `ALWAYS_ON_ACCOUNT_EXECUTION_REQUIRED=1`, including the core plugin. They start closed and require a fresh, memory-only controller grant; Host restart never restores permission. The controller renews every 10 seconds with a maximum 30-second lease measured using the authority's monotonic clock from **request reception**, not queue completion. Persisted revisions prevent delayed older grants reopening work. Lost controller contact expires permission. The native Agent/public LLM-stream/tool gates reject new work, request in-flight native Agent cancellation and pause owned native schedules. Resume restores only account-paused active schedules, preserving IDs and explicit user pauses. Failed native schedule restoration becomes an explicit task error, not silent success/replay. The push worker also waits while execution is denied.

This is bounded execution authorization, not a second Agent loop or a cloud shutdown. Already dispatched provider requests/external effects cannot be undone or refunded, cancellation is best effort, and container/VM charges continue. Old authorities without this policy cannot promise lease-based shutdown: keep them stopped until the coordinated upgrade below. Neither logout nor plugin removal deletes hosted tasks/memory. See [stabilization evidence](../../docs/V03_STABILIZATION.md).

`scripts/control-backup.mjs create <encrypted-file>` requires `ALWAYS_ON_DEPLOYED_SHA` to be the exact 40-character SHA of the deployed image set, plus the exact Compose project/file and an independent `ALWAYS_ON_BACKUP_KEY_FILE`. It validates all seven existing mounted volumes and refuses unrelated running writers before stopping anything. It stops the selected stack, snapshots controller/agent/config/edge volumes together, encrypts the checkpoint, then starts **only the original container IDs that were already running**. It does not reconcile an edited Compose file or deploy a retagged image during backup. Previously stopped services remain stopped. Retain that key, the control encryption key and operator configuration securely outside the running Host. Run during an approved maintenance window. Restore authenticates the full checkpoint before touching volumes and requires `--replace-stopped-volumes`; it is destructive to those stopped volumes. New format-2 checkpoints also record actual container image content IDs. Restore checks the images selected by the current Compose configuration against those IDs before stopping or changing volumes; simply setting the source-SHA variable is insufficient. Format-1 checkpoints lack this evidence and require an explicitly reviewed `--allow-unverified-legacy-images` recovery; they are not silently promoted to image-verified backups. Successful restore resumes only previously running service names with `--no-deps`, using those verified images. Decrypted temporary archives are removed even if restart fails. Restore requires the exact recorded deployed SHA; restore the complete matching checkpoint into that recorded runtime first, then run migration and interrupted-state checks. Do not substitute the checkout SHA of a newer operator shell. Pin deployed images by reviewed digest and retain the corresponding source/configuration. If any volume restore fails, the tool keeps the whole stack stopped; complete the consistent checkpoint restore before restarting. **No production backup/restore rehearsal is claimed yet.** CI verifies seven disposable volume backups/SQLite migrations and a real previous-image → new-image → encrypted-checkpoint rollback of native Harness state; five non-agent volumes in the image test are fixtures. This is not a configured production full-stack restore.

Pin image/package/source revisions for deployments. Before updating, save a coordinated encrypted checkpoint and record the deployed SHA. Gateway schema v2→v3 preserves identity/operations and adds account budgets; core memory JSON adds an optional revision without changing IDs. Control schema 1→2 transactionally adds account suspension and execution revisions while preserving accounts/devices/allocations; managed gateway schema remains 3 (policy metadata only). Upgrade core, managed and controller together from one coordinated stopped checkpoint, set the required-execution environment flag before starting account profiles, then start the controller and verify fresh grants plus private native schedule status. Do not run a pre-lease authority with a new controller and claim fail-closed behavior. Newer DB versions refuse downgrade. Roll back images **and their matching complete checkpoint**, never mount a newer database under an older binary or reset account mappings independently of agent volumes.

## Trusted edge and login rate limits

The provided topology has **one directly exposed Caddy edge**. It overwrites `X-Always-On-Client-IP` with the actual TCP peer on both public route groups. The controller accepts that single canonical IP only from its exact configured trusted peer, matching public Host and HTTPS forwarded protocol; untrusted XFF/Forwarded/custom headers are not identity. Separate client, account, device and proof-bound login-session buckets avoid one shared Caddy address exhausting every user's login allowance. Health checks explicitly supply approved Host/protocol/client headers on the private controller network. Do not place an unreviewed CDN/load balancer in front: that changes the address trust boundary and requires separately configured/retested trusted edge handling, never blind trust of arbitrary X-Forwarded-For.

## Existing v0.2 owner migration

Automatic pool allocation deliberately refuses nonempty legacy profiles. Preserve them; never reset IDs or infer ownership from matching email. After the operator verifies the signed-in account's ownership of the old authority, records the exact control account UUID, saves a coordinated checkpoint and stops that Host, the private `scripts/managed-admin.mjs adopt-account ACCOUNT_ID --verified-ownership-and-stopped-host --revoke-legacy-devices` command binds that same gateway identity and revokes legacy device/push credentials. It does not rewrite Tasks, Memory, Inbox, Run Ledger or native Sessions. Put that **existing isolated slot** in the account's reserved pool mapping and restart it; the controller must see the same authority/owner UUIDs. Another account binding or reusing a volume for another user is refused. This is a privileged operator procedure requiring real ownership evidence, not an end-user pairing workaround or a claimed production migration rehearsal.

## Bounded device reads and record export

The shared client automatically falls back from a small `/snapshot` to device-bound `/snapshots` pages. Each immutable snapshot expires after five minutes; pages are bounded by 128 KiB or 100 records, with a 64 MiB snapshot ceiling and four concurrent captures. Export and state cursors have separate scopes. Expired cursors require a fresh capture; an unfinished JSONL export has no completion footer and must not be shared as a complete export. Capture limits are separate from ordinary API admission: three exports/minute/device and ten/account; twelve state captures/minute/device and sixty/account. These are resource bounds, not unlimited archival storage.

Desktop downloads and phone app-private file sharing export Tasks, Goals, Memory, Inbox and Run Ledger; they exclude credentials and native Session transcript bytes. Recent UI activity is bounded to 200 Run/Inbox records; the complete retained ledger is available through record export. Memory deletion prevents future retrieval/injection; an earlier immutable export snapshot remains readable until its five-minute expiry. Running-server cleanup checks expired files every 30 seconds and startup purges all temporary captures; stopped volumes and backups retain bytes until cleanup/retention processing. Already downloaded files, historical Sessions, provider records and retained encrypted backups are not retroactively erased. Rotate backups according to the reviewed retention policy.
